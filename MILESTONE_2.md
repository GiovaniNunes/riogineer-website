# Milestone 2 — implementation report

The specification interpretation layer is implemented before the approved deterministic workflow at `/digital-engineer`. PDF/text interpretation produces a reviewable draft only. Approval requires resolved review checks and the unchanged Python requirements validator. PFD generation and calculation remain separate user actions.

The original reference folders were not modified. The Milestone 1 contracts, evaluator, Python engine, API proxy and original numerical/validation tests were preserved. No deployment, persistence, authentication, graphical PFD editing or broader equipment support was added.

## 2. Interpretation architecture

```text
PDF bytes → isolated text-only worker → page text ┐
Typed specification ────────────────────────────┼→ source-by-source LLM interpretation
Additional instructions ────────────────────────┘
    → strict draft schema + exact citation checks + signed draft
    → WHAT RIOGINEER UNDERSTOOD
    → engineering form corrections, assumption decisions, conflict resolution
    → APPROVE REQUIREMENTS
    → requirements v1.0 + approval provenance
    → unchanged Python validation
    → GENERATE PFD → flowsheet v1.0 → read-only PFD
    → RUN ENGINEERING CALCULATION → unchanged Python evaluator → results v1.0
```

There are no mass/energy balance equations in the interpretation layer. Its arithmetic is restricted to explicit unit normalization and checking that a supplied total feed rate agrees with supplied component rates. It does not infer component rates from a total/composition, invent the remaining recovery fraction, normalize recoveries or predict properties.

The capability manifest exposes exactly one feed, one three-phase separator, gas/oil/water outlets, prescribed component recoveries and constant-Cp energy accounting. Fixed identifiers and registered model options are application metadata; missing numerical engineering inputs remain missing.

## 3. Supported inputs

- A text-based PDF.
- A typed/pasted engineering specification, up to 20,000 characters.
- Additional instructions, up to 20,000 characters.
- Any combination of these, retaining separate `document`, `specification` and `instructions` source IDs.

No fixture is substituted for a missing provider. The Bia reference remains available only in the explicit advanced deterministic workflow for regression/developer use.

## 4. LLM provider boundary

`InterpretationProvider.interpret_specification(source, capability_manifest)` returns untrusted draft data. The orchestration service invokes it separately for each supplied source and validates/combines the returned facts without assigning precedence to a document or user instruction.

The included adapter uses a configurable HTTPS Chat Completions endpoint, model and server-side bearer credential. JSON object mode is followed by strict local schema validation. Malformed, refused or truncated completions are rejected. The adapter follows the [official JSON output documentation](https://developers.openai.com/api/docs/guides/structured-outputs); JSON mode alone does not establish schema or engineering validity.

A future private/local adapter can implement the same interface without altering review, requirements, flowsheet, results or the engineering engine. A local inference runtime is intentionally not implemented. The included cloud adapter requires HTTPS; its URL is operator configuration, never document-controlled input.

Provider calls have a 45-second timeout per source and a 512 KiB response limit. Provider error bodies and credentials are not returned to the browser. No tools, code execution or engineering operations are exposed to the LLM.

## 5. PDF extraction

- PDF filename/type and `%PDF-` signature checks.
- Maximum upload: **5 MiB**; maximum **40 pages**; maximum **60,000 extracted characters**.
- Uses pinned `pypdf==6.19.0` in a separate Python worker, independent of the engine process. It reads page content streams for text only; no embedded JavaScript, actions or attachments are executed.
- All document bytes are passed over stdin; no temporary upload file or permanent storage is created.
- Encrypted, malformed, oversized, excessive-page and textless PDFs receive explicit errors. No OCR or inference from unreadable content.
- A partially textless PDF reports empty pages as a blocking review ambiguity; the user must explain their review of the omitted content.
- Parent wall-clock timeout: 15 seconds; worker CPU limit: 10 seconds; 768 MiB address-space limit where the OS supports it; bounded stdout.
- Worker logs/stderr are suppressed and errors contain no server filesystem paths.

Text extraction cannot establish that all graphical/table information was captured correctly. Exact extracted excerpts and page numbers support the mandatory review. See the [pypdf extraction limitations](https://pypdf.readthedocs.io/en/stable/user/extract-text.html).

## 6. API endpoints

| Endpoint                                             | Input                                                                       | Successful response                                                                        |
| ---------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `POST /api/digital-engineer/interpret-specification` | Multipart fields `document` (optional PDF), `specification`, `instructions` | Versioned signed interpretation envelope; no calculation                                   |
| `POST /api/digital-engineer/approve-requirements`    | JSON `{ draft, signature, review }`                                         | The unchanged validation response containing approved `requirements` and Python validation |

Both require a matching browser origin, enforce bounded inputs and return `Cache-Control: no-store`. Approval verifies the original draft signature, repeats review gating on the server, enforces the existing 128 KiB engine document limit and calls the existing deterministic validation API adapter. A forged/deleted issue cannot be used to bypass review through this endpoint.

The existing `validate-requirements`, `build-flowsheet` and `calculate` endpoints remain intact. The advanced/manual contract workflow and engine API continue to support Milestone 1 use; approval is a review control for interpreted specifications, not authentication or a new restriction on those existing developer APIs.

## 7. Review and approval

The progression is Specification → RIOGINEER interpretation → Review & approve → PFD → Simulation → Engineering results.

The review shows process/topology, feed/component data, separator conditions, separation model, model inputs, outputs, missing information, ambiguities, conflicts, assumptions and unsupported requests. Forms expose units and expandable exact source evidence. Users can enter absent values, correct interpreted values or explicitly select a cited alternative.

Every proposed assumption has an individual accept/reject control. Rejecting a required assumption requires a user replacement. The user must separately acknowledge the registered development model and its limitations. The browser disables approval while blockers remain; the server independently repeats the same review checks.

Approval validates but does not build a flowsheet or calculate. A validation failure remains visible with the engine's issue details. The raw requirements/flowsheet/results are in the initially collapsed **Engineering data / Advanced** section. Downloads remain available; stale results cannot be downloaded as current.

Source edits, corrections, premise decisions and re-interpretation invalidate approval/PFD/results immediately. Original results remain visible as stale. Request revisions prevent late interpretation, approval, PFD or calculation responses from replacing edited inputs. Display-only PFD layout changes still preserve current results.

## 8. Provenance and unchanged engineering contracts

Each interpreted fact retains its value, original unit, specified/assumed origin, source type/ID, exact excerpt, PDF page where available and confidence. The server verifies that the cited excerpt exists on the cited source page. LLM-derived engineering facts are rejected; derived entries in approved provenance are deterministic unit conversions only.

Corrections are recorded as user-specified with the previous interpretation preserved. Assumption decisions, resolution notes, model acceptance, approval time, original source metadata and SHA-256 hashes of extracted page/text data are retained. The source hashes are hashes of extracted source representations, not original PDF file bytes.

**Compatibility choice:** the unchanged v1 contract already has a free-form `provenance.source` string. Approved interpreted requirements store a JSON-encoded audit envelope in that string:

```text
format: riogineer.interpretation-approval
version: 1.0
interpretation: original versioned draft, sources, facts and issues
review: user corrections, assumption decisions, resolutions and model acceptance
approved_at / status
normalized_values: canonical values, original units, origin and review evidence
model: registered capability manifest
```

Consumers can read it with `JSON.parse(requirements.provenance.source)` when `format` matches. The existing `basis: synthetic_development_assumptions` is retained because this remains the approved development model. No schema field, validation rule or fingerprint calculation was weakened. The unchanged requirements hashing includes this audit string, so revised approved requirements have a different identity.

A server-generated HMAC protects the original review draft without a database. The default signing key lasts for the server process; restarting requires re-interpretation. A configured signing secret can maintain consistent verification across local workers/restarts. This is not an identity/authentication feature.

## 9. Missing data, ambiguity and conflict behavior

- Required fields are enumerated from the supported model independently of the provider's missing-data report.
- Bare `bar` and gauge pressure remain unresolved; no atmospheric pressure or absolute-pressure basis is invented.
- Supported explicit conversions: °C→K, bar absolute→Pa absolute, kg/s→kg/h, kJ/(kg K)→J/(kg K), percent→mass fraction. Other units require explicit user correction.
- All three recoveries for every component must be supplied. The unchanged Python engine checks sums, positive total feed, component keys and pressure consistency.
- Different values for the same fact create a conflict even if the provider omitted a conflict warning. Neither source wins automatically. An explicit correction/selection is required and all alternatives remain in provenance.
- A supplied total inconsistent with component flows blocks approval.
- Field-linked ambiguity/conflict issues require a resolution note and a reviewed field value. General ambiguity requires an explicit resolution note.
- Unsupported issues cannot be dismissed into a supported calculation; revise the specification and interpret again.

## 11. Known limitations

- One feed and one three-phase separator only. Prescribed recoveries and constant Cp remain development assumptions; no rigorous equilibrium, latent heat, sizing, geometry-based efficiency or arbitrary topology.
- No OCR, image/diagram interpretation, password-protected PDF support or automatic reconstruction of PDF tables. Modern browsers and a local macOS/Linux Python runtime are expected (Windows can use WSL).
- A total flow and fractional composition alone do not automatically become component mass flows; users must supply those required inputs explicitly.
- Source citations are checked for exact occurrence, not semantic truth. Human review remains required. A provider may miss or misinterpret a requirement; unsupported/ambiguous extraction must be corrected or reinterpreted.
- Changing the component basis to remove/rename existing components may require re-interpretation; orphan component inputs are blocked rather than silently discarded.
- Long evidence histories can reach the preserved 128 KiB engine request limit; approval then returns a clear error instead of dropping evidence.
- No document/project persistence. Reload loses unsaved review work; use the approved structured downloads. Cloud provider retention/data policy is separate from the application's no-storage behavior.
- The included provider adapter was validated with controlled test responses. No paid/live external-model call or provider-specific accuracy evaluation was performed. Live behavior requires the operator's chosen compatible model and credentials.
- No accounts, authentication, database, billing, deployment or local inference runtime. Existing advanced JSON APIs are not an authenticated approval boundary.

```sh
npm ci --cache .local/npm-cache
python3 -m venv engine/.venv
engine/.venv/bin/python -m pip install -r engine/requirements.txt -r interpretation/requirements.txt
```

Terminal 1, from the repository root:

```sh
cd engine
.venv/bin/python -B -m riogineer_engine.server --port 8001
```

Terminal 2, from the repository root:

```sh
export RIOGINEER_PDF_PYTHON="$PWD/engine/.venv/bin/python"
npm run dev
```

Open `http://127.0.0.1:3000/digital-engineer`, or the port Next.js prints. If a development server is already running, use that server; restart it after updating provider environment settings.

To enable live interpretation, add the variables in section 13 to `.env.local` (preserve any existing settings; do not commit credentials). Without them the UI reports exactly **“Specification interpretation is not configured.”** The deterministic advanced workflow can still run with the local engine.

## Follow-up corrections after the first live interpretation

The user reported that live interpretation succeeded, but the returned `gas,oil,water` value was displayed as unsupported. Inspection found exact-string comparisons against `gas, oil, water` in both the review UI and approval logic. The provider contract represents the output list as a text fact; it was not being split into identifiers.

The shared review layer now recognizes the individual `gas`, `oil` and `water` identifiers across comma spacing, the conjunction “and,” case and order. It checks the complete identifier set and never filters away unknown outputs. Unsupported products and unsupported-capability issues remain blocked. Formatting-only differences do not create spurious source conflicts. The original signed fact and excerpt are unchanged; the approval audit also records `normalized_output_ids`.

Ordinary missing required numerical inputs now receive accessible field highlighting and a single named entry in **Required review checks**. The **Missing information** section provides the concise completion instruction instead of repeated generic issue cards and resolution-note boxes. Original missing issues remain in provenance. Supplying a valid value resolves the missing-input check; a note cannot substitute for a required value.

Ambiguities, explicit conflicts and unclassified interpretation issues retain explanatory notes. Contradictory source facts also require a resolution note alongside the chosen/replacement value, even if the provider omitted a conflict issue. Server-side approval repeats these checks; the Python validator and all Milestone 1 calculations are unchanged.
